# 트립메이트 – 여행 일정 변경 대응 AI Assistant

## 문제 정의

### 해결하려는 문제
토요일 서울 당일 여행 중인 4인 일행은 출발 당일 아침, 비 예보 강화(D04), 오후 지하철 지연 안내(D06), 전망대 야외 데크 폐쇄 가능성(D05)을 동시에 맞닥뜨렸습니다. 정보마다 성격이 다르고, 공연 입장 마감이나 예약 규칙은 확정 조건인 반면, 강수확률·이동시간·지연시간은 바뀔 수 있는 예보와 추정입니다(D08). 또한 결정마다 시한이 다르며, 예를 들어 미술관 예약은 09:30이 지나면 환불되지 않으므로(D02) 지금 판단해야 하고, 한강공원·전망대 일정은 오후 상황을 보며 조정할 수 있습니다. 일행은 지금 상황에서 무엇을 유지하고 무엇을 바꿀지를 이유와 함께, 그리고 확실하지 않은 것은 확실하지 않다고 알려주는 도구가 필요합니다.


### 핵심 판단 기준
1. **공연(18:40 입장 마감)은 절대 조건입니다.** 일행 모두의 최우선 일정이므로(D01, D02), 이동시간과 지연을 최악의 추정치로 적용해도 지킬 수 있는 안만 추천합니다.
2. **예약된 일정은 최대한 유지합니다.** 미술관·식당은 가기로 하면 입장 시간대와 지각 한도 등 예약 규칙을 지켜야 합니다(D02).
3. **날씨에 따라 바꿀 수 있는 야외 일정을 우선 조정합니다.** 한강공원 체류와 전망대 야외 데크는 날씨·교통 조건에 따라 유지/축소/대체합니다(D04, D05, D07).
4. **예보와 추정은 확정 사실처럼 표현하지 않습니다**(D08). 자료에 없는 값을 가정한 경우 "가정"으로 표시합니다.

### 프로그램이 제공하는 결과
- 유지할 일정과 변경 가능한 일정 1~3순위
- 각 추천의 이유와 근거(D01~D08 문서 번호 또는 사용자 입력값)
- 불확실성: 판단에 영향을 준 예보·추정·가정값
- 사용자가 확인할 항목: 현장에서 직접 확인해야 할 사항

입력값(현재 시각, 강수확률, 풍속, 지연시간, 입장 마감 등)을 바꾸면 소스코드 수정 없이 다시 실행할 수 있으며, 조건에 따라 추천 순위와 근거가 달라집니다.

## 실행·사용 방법

**필요 프로그램**: Python 3.10 이상. 외부 패키지는 쓰지 않습니다(표준 라이브러리만). 개발 환경은 Python 3.15.0이었습니다.

**실행 명령**
```
python tripmate.py --no-llm          # 규칙 결과만 출력
python tripmate.py                   # 규칙 결과 + LLM 요약
python tripmate.py --input 내입력.json --now 09:45 --rain 20 --wind 4
```

| 옵션 | 내용 |
|---|---|
| `--input` | 입력 JSON 경로. 기본값은 `input/default.json` |
| `--now` | 현재 시각(HH:MM). 미술관 환불 마감 전후 판단에 씁니다. |
| `--rain`, `--wind` | 강수확률(%), 평균 풍속(m/s) |
| `--delay MIN MAX` | 한강공원→전망대 지하철 추가 지연(분) |
| `--concert-deadline` | 공연 입장 마감(HH:MM) |
| `--buffer` | 공연 입장 전 안전 여유(분) |
| `--no-llm` | LLM을 호출하지 않습니다. |

**입력 파일**: [input/default.json](input/default.json)의 값은 모두 `{"value", "source", "kind"}` 형식입니다.
- `source`: 근거 문서(D01~D08) 또는 사용자 입력
- `kind`: fixed(확정) / estimate(추정) / preference(선호) / assumption(자료에 없어 사용자가 정한 가정) / input(입력)
- 체류시간, 택시 요금, 우천·강풍 판단 기준, 안전 여유, 순위 가중치는 자료에 없는 값이라 `assumptions`와 `weights`에서 바꿀 수 있습니다.

**사용 순서**
1. 입력 파일이나 CLI 옵션으로 현재 시각과 최신 예보·지연 정보를 넣습니다.
2. 실행한 뒤 다음 순서로 확인합니다.
   1. 공연 입장 점검
   2. 현재 유지할 일정
   3. 변경 가능 일정 1~3순위
   4. 탈락한 조합
   5. 불확실성
   6. 사용자가 확인할 항목
3. "사용자가 확인할 항목"을 현장에서 확인한 뒤, 바뀐 값으로 다시 실행합니다.

**판단 방식 요약**
- 한강공원(유지·축소·실내 대체) × 전망대(데크 포함·실내층만) × 한강공원→전망대 이동수단(지하철·버스·택시)을 조합해 18개 후보를 만듭니다.
- 모든 이동시간은 추정 범위의 최대값으로 계산하고, 지연 시간대에 걸리는 구간에는 지연 최대값을 더합니다.
- 다음 확정 조건 중 하나라도 어기면 후보에서 뺍니다.
  - 공연 입장 마감(안전 여유 포함)
  - 미술관 입장 시간대
  - 식당 지각 한도
  - 전망대 실내층 입장 마감
  - 택시 횟수와 교통비 예산
- 남은 후보는 점수(공연 여유, 비 예보 시간대 야외 노출, 한강공원 방문 희망, 데크 위험, 교통비)로 순위를 매깁니다.
- LLM은 규칙 결과를 요약하는 문장만 만듭니다. 호출이 실패하거나 응답에 D08 금지 표현이 들어 있으면 규칙 결과만 출력합니다.

## 검증 결과

2026-10-20에 실제로 실행한 결과입니다. 자동 단위 테스트는 없고, 아래 명령을 직접 실행해 출력을 확인했습니다.

**하드코딩 수정 후 다시 실행한 결과** (`--no-llm`)

| 시험 자료(명령) | 예상 결과 | 실제 결과 |
|---|---|---|
| 기본 입력 (강수 80%, 풍속 9m/s, 현재 09:25) | 한강공원 축소·실내 대체, 데크 제외 안이 상위. 미술관 취소 여부가 확인 항목에 나옴 | 1순위: 한강공원 30분 축소 / 실내층만 / 지하철. 최악 추정 공연장 도착 17:35(여유 65분). 통과 16개, 탈락 2개. 유지 일정: 공연·미술관·식당·전망대 실내층(상위 3개 안 공통). 미술관 확인 항목: "2명이 꼭 가고 싶어 해서 유지 쪽을 권장함". 지하철 지연 확인 항목 출력 |
| S1 `--rain 20 --wind 4` | 한강공원 유지, 데크 포함 안이 1순위 | 1순위: 한강공원 유지 / 실내층+데크 / 버스(도착 18:10, 여유 30분). 상위 3개 안 모두에 한강공원 야외가 들어가서, 유지 일정에 "한강공원 P 야외"가 추가로 계산됨 |
| S2 `--now 09:45` | 미술관 취소 확인 항목이 사라지고 "환불 불가" 근거가 붙음 | 예상대로. 미술관 유지 항목에 "환불 마감 09:30이 지나 취소해도 환불 불가 [확정 D02]" 추가 |
| S3 `--delay 50 70` | 지하철 경유 안이 불리해짐 | 1~3순위 이동수단이 모두 버스로 바뀜. 통과 14개, 탈락 4개. 지연 확인 항목의 근거가 `[추정 CLI 입력]`으로 바뀜 |
| S3' `--concert-deadline 18:10` | 탈락이 늘어남 | 통과 12개, 탈락 6개. 1순위는 기본 입력과 같음(여유 35분) |
| `--concert-deadline 17:00` | 통과 안 없음 | 18개 모두 탈락. 유지 일정에는 공연만 남음. 지하철 지연 확인 항목은 나오지 않음(평가할 상위 경로가 없음) |
| 미술관 `wanted_by`=0 (코드에서 값만 바꿔 실행) | 유지 권장 문구가 바뀜 | "꼭 가고 싶은 인원이 없어 취소도 검토할 수 있음" 출력 |

**확인된 오류와 조치**
- LLM 요약이 길이 제한(600토큰)에서 잘림 → 1500토큰으로 늘린 뒤 다시 실행해 요약이 끝까지 출력되는 것을 확인했습니다.
- LLM 요약이 체류시간 가정값(사용자 입력)에 근거 "(D03)"을 잘못 붙인 사례가 있었습니다. 판단은 규칙 결과 기준이며, 요약의 근거 표기는 검증하지 않습니다(알려진 한계).
- S3에서 `--delay 50 70`을 줘도 "축소 + 지하철" 안은 여전히 조건을 통과합니다(전망대 출발이 지연 시간대보다 이릅니다). 1순위가 버스로 바뀐 이유는 같은 점수에서 최악 이동시간이 더 짧기 때문입니다.

## 구현 범위

**완성**
- 입력 JSON(근거 D번호, 확정·추정 구분)과 CLI로 값 바꾸기
- 최악 추정치 기준 공연 입장 점검과 확정 조건 하드 체크
- 유연 일정 18개 조합 평가와 1~3순위 출력
- 출력 각 항목의 근거 태그
- 미술관 환불 마감 전후 분기와, 희망 인원(`wanted_by`)에 따른 유지·취소 검토 문구
- 상위 후보들에 공통으로 포함된 일정을 계산해 "현재 유지할 일정"으로 출력
- 지연 확인 항목은 상위 안의 경로가 지연 시간대를 지날 때만 출력
- 불확실성·사용자 확인 항목 출력
- LLM 요약과 실패 시 규칙 결과만 출력

**미완성**
- 자동 단위 테스트(unittest)
- JSON 형식 출력
- 통과 안이 없을 때의 "공연만 지키는 최소 경로" 계산: 식당→공연장 같은 구간의 이동시간 자료가 없어 탈락 사유만 출력합니다.

**한계**
- 체류시간, 택시 요금, 교통비 단가, 우천·강풍 판단 기준, 점수 가중치는 자료에 없어 가정값을 씁니다. 결과가 이 값에 따라 달라집니다.
- 택시로 시간을 줄이는 효과는 한강공원→전망대 구간에만 반영했습니다. 다른 구간은 최악값 기준이라 단축분을 0분으로 봅니다(D03).
- 버스·택시 소요시간(D06)은 선로 점검 시간대 밖에도 같은 값으로 적용합니다.
- 공연 여유는 30분을 넘으면 점수에 더 반영되지 않습니다(`weights.slack_cap_min`).

코드 점검에서 찾았지만 아직 고치지 않은 하드코딩은 다음과 같습니다.

*순위*
- 점수가 같으면 후보 생성 순서(지하철→버스→택시)로 순위가 정해집니다. 기본 입력의 1순위인 "지하철"이 이 경우입니다(`planner.py` 정렬).
- 출력 순위 개수(3개)와 후보 선택지(한강공원 3종, 전망대 2종)는 코드에 고정돼 있습니다.

*시간·비용 계산*
- 방문 순서(서울역→미술관→식당→한강공원→전망대→공연장)와 구간 이름은 코드에 고정돼 있어 입력으로 경로를 바꿀 수 없습니다.
- 한강공원→전망대 외 구간은 지하철만 계산합니다.
- 한강공원 "축소" 체류시간으로 비 올 때 야외 최대 시간(30분)을 씁니다. 비가 오지 않는 조건에서도 같은 값이 쓰입니다.
- 데크 체류는 전망대 도착 직후에 시작한다고 가정합니다.
- 택시는 일행 전체가 1대에 탄다고 보고 1회 요금만 더합니다. 인원 수는 반영하지 않습니다.
- `--delay`는 입력 파일의 모든 지연 항목을 한꺼번에 덮어씁니다.

*문구·근거 태그*
- 장소 이름("미술관 M" 등)과 선택지 라벨은 입력 파일이 아니라 코드에 있습니다.
- 다음 근거 태그는 입력 `source` 대신 문자열로 고정돼 있습니다.
  - 순위별 이유의 지연 근거 "D06"
  - 불확실성의 이동시간 근거 "[추정 D03]"
- "방문 희망은 일부 반영", "일행이 허용한 대체 방식" 같은 평가 문구는 고정돼 있습니다.
- 통과하는 안이 없을 때 "유연 일정을 생략하고 공연장 이동을 우선 검토"는 계산 없이 나오는 고정 문구입니다.
- 탈락 사유는 문장 앞 두 단어로 묶습니다. 문구가 바뀌면 묶음 결과도 달라집니다.

## LLM 설정

LLM 연결은 [llm_client.py](llm_client.py)가 맡습니다. Anthropic Messages API 방식이며 Python 표준 라이브러리만 사용합니다. 접속 주소와 키는 환경변수로만 읽습니다.

1. `.env.example`을 `.env`로 복사합니다.
   ```
   cp .env.example .env
   ```
2. `.env`의 각 변수에 값을 입력합니다.

   | 변수 | 내용 |
   |---|---|
   | `ANTHROPIC_BASE_URL` | LLM 접속 주소. 끝에 `/v1/messages`가 붙어 호출됩니다. |
   | `ANTHROPIC_API_KEY` | API 키 |
   | `ANTHROPIC_MODEL` | (선택) 모델 이름. 비우면 코드의 기본값을 씁니다. |

3. 연결을 테스트합니다.
   ```
   python llm_client.py "짧은 테스트 메시지"
   ```

- `.env`는 `.gitignore`에 들어 있어 커밋되지 않습니다. 키 값은 코드나 문서에 쓰지 마세요.
- 셸에 같은 이름의 환경변수가 이미 있으면 `.env`보다 그 값이 먼저 쓰입니다.
- 호출이 실패하면 `LLMError`가 발생합니다. 프로그램 본체는 이 오류를 잡고 규칙 기반 결과만 출력해야 합니다.
